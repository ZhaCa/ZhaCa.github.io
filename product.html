01

管理企业 Agent 的生产生命周期

企业往往已经在多个平台上创建了 Agent。进入生产后，真正需要回答的是：谁负责、当前运行哪个版本、能够使用什么资源、任务是否完成、质量为何下降，以及下一次改进是否有效。

ASSET

看清企业有哪些 Agent

统一台账连接来源、Owner、版本、模型、工具、Skill 与知识引用，保留外部运行和平台托管的能力差异。

EVIDENCE

解释任务为什么成功或失败

从业务目标进入 Session、Trace、Span 和行为轨迹，区分技术完成与业务结果，避免只看调用成功率。

IMPROVEMENT

让改进进入真实运行版本

失败轨迹入集，比较基线与候选，经过审批和发布，再用新任务验证效果，形成可追溯的改进链。

02

运行管理与持续优化，共用一条流程

借鉴 AgentCore 拆解中的运行与资源管理，以及 AgentLoop 拆解中的质量迭代思路，将运行底座、观测证据和版本改进连接到同一产品流程。

  1. 接入 / 部署已有 Agent、来源与制品
  2. 资源与权限模型、工具、身份及授权
  3. 测试评估样本、基线、准入检查
  4. 发布运行审批、版本、实例与任务
  5. 观测诊断指标、调用链、行为轨迹
  6. 评测优化Bad Case、候选与对比
  7. 回归发布门禁、回退与效果验证

运行管理主线

从资产与部署制品开始，管理资源依赖、执行身份、环境、任务协作、实例、配额和检查点，保障 Agent 能在明确范围内执行。

核心对象：Agent → AgentVersion → Deployment → Runtime → Task

持续优化主线

采集并解释运行证据，把质量问题变为样本和版本变更，经过同集比较与发布门禁，验证改进是否真正进入生产。

核心对象：Trace / Trajectory → DatasetCase → EvalRun → Experiment → Release
贯穿能力： 身份权限与策略 · 安全与审计 · 费用与预算 ｜异常进入事件处置；退出经过停流、撤权与归档。
技术执行 ≠ 业务结果工具调用返回成功，仍需要业务系统终态或人工成果审核。
采集健康与运行健康分别观察停报表示证据缺失，不能推定 Agent 正常，也不能直接推定 Agent 已停止。
源接受与效果生效分别核验控制经过申请、审批、发送、回执、效果验证，不能凭一个成功回执关闭事件。
经验入库与运行加载分别管理样本、复盘或知识引用发生变化后，需要评测与发布，才会改变运行版本。

十个模块，围绕三个详情枢纽协同

Agent 全景说明“管理谁”；任务详情说明“执行了什么、结果如何”；版本详情说明“改了什么、凭什么发布”。模块之间通过同一对象 ID 和证据链连接。

输出
待处理对象、异常入口与完整场景导览

发布与治理

事件中心

围绕影响对象组织诊断与处置计划，管理受控动作、源回执、效果和双重恢复核验。

输入
业务异常、Team 诊断、控制能力
输出
控制命令或人工工单、恢复证据与复盘
查看运维事件 ↗
评审：事件关闭前置条件
技术恢复与业务恢复均须完成；业务核验未通过不能关闭。无控制接口转本地人工工单。控制超时只允许人工确认后沿原幂等键重试。

成本中心

区分原厂账单、用量估算、缺失与未归属费用，按 Agent、任务和部门理解开销。

输入
来源账单、模型 / 工具 / 运行用量与部门映射
输出
费用归属、预算状态与当前空间导出
查看成本中心 ↗
评审：成本口径
缺失金额为 null，不能当作零；估算不能替代账单。费用归属不改变总金额；优化节省需结合相同工作负载、质量与真实账单验证。

平台设置

维护组织空间、成员访问、数据策略、凭据引用及模拟接口，集中管理演示与需求评审。

输入
组织成员、区域、保留与访问规则
输出

查看平台设置 ↗
评审：生产安全边界
角色和空间限制在本地模拟接口统一校验；凭据仅保存引用。浏览器本地数据库、管理员全权限演示与审计不能替代生产认证、安全隔离和不可篡改存储。
04

从单 Agent 改进，到 Team 协作

单 Agent：从一次错误答复改进运行版本

  1. 研发登记已有 Agent，关联来源、模型、工具与执行身份。
  2. Owner 导入测试样本，研发运行基线评测，建立优化候选。
  3. 候选版本完成回归和同集比较，提交上线申请。
  4. 业务审核人与安全审计员分别审批，研发执行发布。
  5. 运行中发现失败任务，沿 Trace 进入行为轨迹，将问题加入回归集。
  6. 在新样本快照上重新评测基线和候选，发布修复，并核验新任务业务结果。
每一步都关联版本和证据。修改候选不会直接改变运行 Agent。

AgenticOps：管理协作目标与成果

  1. Team 接收业务目标，Leader 按成员职责分派子任务。
  2. 成员使用各自版本和授权资源执行，保留任务、Trace 与行为轨迹。
  3. Owner 复核成果；证据不足或成员失败时退回修改。
  4. 修订重新提交，保留旧执行尝试和失败原因。
  5. 成员成果汇总；涉及生产动作时进入受控审批。
  6. 业务审核人确认最终成果，区分成员技术完成与整体业务目标完成。
从“多个 Agent 各自可运行”，扩展到“协作过程可追踪、成果可审核”。
评审：三个详情页如何承接流程
Agent 全景：连接资源、运行版本、候选版本、任务、评测、事件和费用。
任务详情：连接目标对象、父子任务、Session、调用证据、行为轨迹和业务核验。
版本详情：连接配置差异、制品引用、数据集快照、评测、实验、审批与部署。
相同工作空间内跨页保留上下文；切换空间后不继续沿用旧空间对象与筛选。
05

企业场景中的产品方案

以虚构企业“星河零售集团”的关联数据演示。AIOps 是重点应用案例；平台同时支持客服、风险业务和跨平台成本管理。

客服 Agent：技术调用成功，答复却不正确

用户在订单号后输入句号，旧版本将标点原样传给查询工具，错误答复“订单不存在”。平台把业务错误转为可复测、可发布的修复。

在原型中这样操作

  1. 进入客服场景，打开失败任务，再进入 Trace，查看 order_lookup 参数。
  2. 以研发工程师将 Trace 加入“客服订单回归集”。
  3. 分别在 v1.8 与 v1.9 版本详情运行同一数据集评测；候选已包含“订单号规范化”修订。
  4. 在 v1.9 运行基线比较，提交发布；分别完成业务放行与安全复核。
  5. 研发在发布记录执行发布，再从 Agent 全景模拟运行。
  6. 业务审核人在新任务核验订单终态，确认修复进入运行版本。
解决方案的结果回答错误具有来源证据；样本沉淀为回归资产；候选与运行版本分别管理；上线后的业务结果继续接受验证。
异常与验收要点
评测失败无分数；样本快照不同不能比较；审批驳回不能发布；发布后任务技术成功仍显示业务待核验。本地评分 72 / 94 为固定规则样例。

从客服 Agent 开始演示 ↗

AIOps：让诊断与处置成为受控协作流程

订单服务错误率上升，需要结合告警、日志、变更记录定位根因。平台组织告警、诊断与处置 Agent 协作，把生产控制和恢复核验交给明确职责。

从告警到经验沉淀

  1. 进入“智能运维”空间，查看订单服务事件及关联 Team。
  2. 运维执行根因诊断，Owner 审核成果；可先退回补充日志，再修订提交。
  3. 完成处置计划并由 Owner 接受，运维执行 Dry-run。
  4. 申请配置回滚控制；安全审计员独立审批，运维再发送请求。
  5. 分别记录源接受回执、核验控制生效，并完成技术恢复。
  6. 业务审核人核对订单服务业务结果；Owner 确认业务恢复、关闭事件并复盘。
结合神州数码智能运维方案以告警分析、根因诊断、运维知识和处置编排为应用输入；AgentOps 负责协作身份、执行证据、控制门禁、恢复确认和持续迭代。
异常与验收要点
前序成果未接受不可执行后续任务；成员失败保留尝试；源接受而未生效时事件保持开放；控制能力缺失时转人工工单；复盘内容不会自动更新运行 SOP。

从订单服务事件开始演示 ↗

退款助手：把高风险动作与业务终态分开

退款 Agent 可以提出动作，但超阈值退款必须经过业务审批。技术调用成功后，仍可能缺少退款终态或产生业务副作用。

风险操作链

  1. 安全人员盘点退款工具和代理用户授权，模拟高风险写操作判定。
  2. 业务审核人审批退款 RF-882；运维执行已获批业务动作。
  3. 业务审核人核对业务回执，可注入“结果不一致”。
  4. 冲突进入事件。运维申请暂停写入控制，业务审核人独立批准。
  5. 发送控制、记录源接受、核验效果；核对副作用后人工确认业务恢复。
解决方案的结果业务动作审批与控制审批分别留证；执行身份和代理用户授权均有有效期；已执行写操作不能自动重放。
异常与验收要点
授权到期阻止执行；未经批准不能执行；二次执行同一写任务被拒绝；技术成功与业务不一致可同时存在；补偿动作需要明确方案与审批，原型不自动退款或重放。

从退款任务开始演示 ↗

多平台：统一资产识别与费用归属

不同部门从多个平台接入 Agent，来源名称和费用口径各异。平台先明确来源与能力，再核对资产身份，保留账单和估算的不确定性。

跨平台管理链

  1. 研发登记来源连接，核验发现、观测和控制范围，设置字段映射与采样。
  2. 登记 Agent；同一连接的原生 ID 不可重复。跨来源同名资产经人工核对后保留主资产及别名记录。
  3. FinOps 按来源区分原厂账单、用量估算和缺失记录。
  4. 将共享工具的未归属费用分配到部门，配置预算并导出当前空间记录。
  5. 优化候选通过质量复测后再发布，后续接入真实账单验证节省。
解决方案的结果减少同名资产误合并；费用缺失不会被显示为零；分配部门不会改变费用总额；数据导出遵守当前空间与环境边界。
异常与验收要点
凭据失效不可同步；不匹配资产不能自动合并；缺失金额不可分摊；账单与估算不直接合计为“已结算成本”。真实计量、对账和复杂分摊规则需后续建设。

从成本中心开始演示 ↗

长任务：可恢复，也要防止重复写入

多 Agent 长任务可能遇到配额排队、运行中断与版本切换。平台需要保留检查点，同时辨别外部业务动作是否已经发生。

运行管理链

  1. 查看部署制品、运行版本、执行身份与实例。
  2. 模拟配额排队，调整容量，保存检查点。
  3. 在确认外部副作用后从检查点恢复；副作用未知时阻止恢复重放。
  4. 对托管实例暂停、恢复或切换流量，核对对应版本。
  5. 扩展高风险工具先申请开通，由独立管理员审批后模拟开通。
解决方案的结果运行资源与发布证据关联；长任务恢复具备明确前置条件；只具备观测能力的外部 Agent 不被误呈现为可控制。
异常与验收要点
无检查点禁止恢复；副作用未知禁止自动重放写操作；来源未接入控制时转人工。当前实例、队列和容量均为本地状态模拟，未创建云资源。
